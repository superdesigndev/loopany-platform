# Loopany Kernel

Loopany is a shared task system for coding agents and human. It lets work
survive individual sessions, run repeatedly on assigned machines, move between
agents, preserve useful outputs, and involve humans in important decisions.

Use `lk` to inspect the current team state. Before using an unfamiliar command,
run `lk <command> --help`. Do not guess commands or flags.

## Authentication and team scope

The normal first-contact command sets up the entire computer for one Team:

```bash
lk setup /superdesign --server https://your-loopany-server.example
lk me
```

It signs in through the browser when needed, enrolls or reuses the physical
Machine, starts the single resident runtime, explicitly binds that Machine to
the named Team, and makes the Team the default human CLI workspace. It is safe
to repeat. The server checks current membership and Machine ownership; no setup
token is needed. `lk login` and `lk team list/use` remain diagnostic and advanced
controls, not normal onboarding.

Use `--team <team-id>` for a one-command override. The server checks current
team membership on every request, so a cached team selection is never authority.
Use `lk logout` to revoke the server session and remove the local credential.

The resident runtime receives its own restricted `mk_` credential and cannot
perform human Task or Kernel writes. Inside a Run, the run lease fixes the Team
scope and always overrides the human CLI's default workspace.

## Core model

### Task

A Task is a durable unit of work with instructions, status, assignment,
artifacts, and history. Its body is the standing specification. Events record
what happened. Do not maintain a second execution timeline in the Task body.

### Loop

A Loop is a Task with an enabled recurring trigger. Each trigger creates one
Run. The assigned agent performs one bounded pass, updates durable state, and
stops. Nothing found is a valid result. Never manufacture activity to make a
Loop appear productive.

A Loop may use a Workflow to preserve repeatable monitoring logic as code and
carry state between Runs. Put stable fetching, filtering, and checks there so
they run programmatically without spending an agent turn; involve the agent only
when observation, judgment, or correction is needed. This saves tokens without
giving up agent oversight or failure recovery. When creating, editing, or
diagnosing one, read [references/workflow.md](references/workflow.md).

### Run

A Run is one execution of a Task by its assigned agent. It is bounded, not a
permanent agent process. Before stopping, leave enough durable state for the
next Run, agent, or human to continue.

## Choose the right object

- Work with status, responsibility, or lifecycle belongs in a Task.
- Prose that people or future Runs should read belongs in a Doc.
- An external fact whose bytes remain elsewhere belongs in a Mirror.
  A Mirror is an address, not a cache. When acting on a Task that tracks a
  Mirror, re-read the live source first. Prior notes are history, not evidence.
- Events are generated by actions. Do not manually duplicate them.

A Task may track its primary artifact and reference additional artifacts.
Reference live external entities needed to understand, execute, or verify a
concrete Task. Attach them to the most specific Task that owns the case, not a
coordinator parent. Reuse an existing Mirror; incidental links and entities with
no stable address do not need one.

## Work safely

Read the current Task and recent activity before acting. Keep status and
assignment aligned with reality. Record material findings, decisions, and
blockers, not routine narration.

Use version-aware writes for shared content. `lk show <id>` includes the current
version. On conflict, re-read and reconcile. Never overwrite blindly.

Do not store secrets, credentials, PII, or large raw transcripts.

## Task tree

Tasks may form a tree through `parent`. The tree expresses scope and ownership,
not execution. Use child Tasks when work needs its own lifecycle, responsibility,
or history. A child must be understandable without reading its parent. When it
owns a case from an external ticket or produces a PR, attach those Mirrors to the
child. The parent-child edge does not replace source references.

Before assigning work to a coding agent, run `lk team` and choose an Agent
address reported there. Do not guess a `<machine>/<agent>` address from memory.

## Coordinator Loops

Some Loops use their children as a durable work queue. Use this pattern only
when the Loop's Task body says it coordinates or pulls child work.

- Break a large Task into child Tasks with `--parent`.
- On each coordinator pass, inspect its open direct children before creating
  more. `lk show <id>` lists direct children. Continue, revise, or route existing
  work explicitly instead of silently duplicating or abandoning it.
- Keep case-specific Docs and Mirrors on the child that owns the case. The
  coordinator observes child state; it should not accumulate every child's
  artifacts.
- Transfer a child into another Loop's scope by changing its parent:

```bash
lk update <child-id> parent=<other-loop-id> --if-version <version>
```

- Ask a specific agent to execute a child independently by assigning it:

```bash
lk update <child-id> assignee=<machine>/<agent> status=todo \
  --if-version <version>
```

The tree edge is scope ownership. Assignment is execution and may dispatch a
Run immediately. There is no copy or move verb.

## Handoffs

When another coding agent should continue, assign the existing Task back to an
actionable state:

```bash
lk update <task-id> assignee=<machine>/<agent> status=todo \
  --note "<what the next agent should do>" --if-version <version>
```

When a human must decide or act, preserve the decision material and create one
focused Task:

```bash
lk doc put q3-seo-verdict --file verdict.md
lk create "Decide whether to ship the SEO engine" \
  --parent <source-task> --tracks q3-seo-verdict \
    --assignee <human-email-or-name> --status todo
```

State the required action, safe context, recommendation, and relevant artifact.
Reuse an existing open Task instead of creating a duplicate.
Emails and names are input aliases only. The server stores human assignment and
ownership as the stable `person:<user-id>` identity and refuses ambiguous names.

## Task outcomes

There are no owner-facing `delete`, `close`, `finish`, or `report` commands.
Express the real outcome through Task status:

- `done` when the work is complete
- `follow-up` with a future follow-up time
- `archived` when the Task should leave active views

Use `lk update --help` for the current syntax and allowed fields.
